## JSONL trace writer moved from the runner into the engine as an adapter
*#160 · PR #161*

The runner's JSONL sink moved verbatim into the engine as
`packages/harness/src/adapters/sinks/jsonl.ts`, a sibling of `reporters/`, exported as
`JsonlTraceSink` with zero format change. The rationale comes from the trace spec: the live stream
and the stored trace are two serializations of the same model, so if the engine ships only one, every
embedder reimplements storage and the stored trace stops being a single format. Four behaviours were
preserved because production depends on them: the sink never throws, because a trace is evidence and
recording must never change a verdict; failures are counted and exposed rather than hidden, so a
truncated trace does not read as a clean one; the path derives from the header's own `runId` so the
filename and header cannot disagree; and writes go through a serial queue behind the synchronous
`emit` with only `close()` awaited. The sink is deliberately not exported from `browser.ts` because
of its `node:fs` dependency.

## Attachment ids are the emitting event's seq, with sidecars resolved by naming convention
*#160*

Attachment ids are the emitting event's `seq`, because a case and step reference cannot distinguish
the two frames a heal produces for the same step: correlating by reference lets one silently
overwrite the other, which is fine for a viewer and wrong for an audit. Multiple attachments on one
event use `<seq>-<k>`. Sidecars are written one file at a time on arrival into a directory named
after the trace file with its extension stripped, with no manifest, because a close-time index
produces the worst failure mode on a truncated run, so the directory listing is the index. Bytes are
always written before the line, so an interruption leaves an unreferenced sidecar rather than an
unresolvable reference. `TraceSink.attach` is optional, and a sink that does not store bytes gets no
reference and no screenshot is taken at all, since an unresolvable reference is worse than none.
`TRACE_VERSION` went 1.0 to 1.1.

## Vacuous assertions get a freeze-time stamp, and all-vacuous fails closed
*#137*

An assertion the starting state already satisfies turns green even if the flow does nothing, so it
has zero discriminating power and is a false green. Discover now takes one baseline observation right
after the entry navigation, and `markVacuous` stamps `AssertionMeta.vacuous` on assertions the
baseline already satisfies; because the stamp rides in the frozen data, replay fails closed when all
assertions are vacuous without needing the baseline, preserving replay determinism. The CLI warns
individually about vacuous proof-type assertions and warns that replay will fail closed when
everything is vacuous. User-authored suite assertions are never stamped, so the gate cannot bite
them. This completes the fail-closed lineage: #69 empty assertions, #90 blocked run, #137 all
vacuous. A side finding: the suite test's crashing-case path depended on exactly this fake green, and
the gate caught it.
