# #225 — 매 턴 요소 목록 보내기

`fix/225-element-listing-every-turn`에서 탐색과 explore 루프가 페이지 요소 목록을 생략하던
동작을 없앴다. 두 루프는 렌더가 직전 턴과 같으면 목록을 `(unchanged from previous step)`
한 줄로 바꿨다. 모델이 직전 턴을 돌아볼 수 있다는 전제인데, `LlmClient`는 대화 없는
`complete(prompt)` 하나이고 제공되는 백엔드 다섯 개가 전부 호출마다 독립 요청을 보낸다.
그래서 두 번째 턴부터 모델은 한 번도 본 적 없는 목록을 가리키는 문장과 페이지에 대한
아무 정보 없이 결정해야 했다.

조건은 렌더가 직전 턴과 같을 때다. 페이지를 바꾸지 않는 동작 하나면 다음 턴이 눈이 먼다.
`waitFor`, 아무것도 드러내지 않은 스크롤, 거절된 동작이 그렇다. 그리고 눈이 멀면 행동할
대상이 없으므로 루프가 회복하지 못한다. 매 턴 페이지가 바뀌는 흐름이면 목록은 계속 간다.
관측된 결과는 이렇다. 실제 모델로 로컬 픽스처 세 개를 여섯 번씩 돌렸을 때 링크 클릭
하나짜리는 12/12 통과했고, 이름 입력 후 저장은 12/12 실패했으며, 로그인·장바구니·주문은
호출 15에서 21회를 쓰고도 완료되지 않았다. 실패한 실행들은 모델의 첫 결정이 `waitFor`라
2턴이 직전과 같아진 경우였다. 모델이
남긴 이유가 "상호작용 요소 목록이 제공되지 않았다"였다. 인지 계층은 정상이었고 첫 턴은
목록이 정확히 나갔다. 돌아온 시나리오는 동작이 하나도 없고 검증 항목이 전부 vacuous라
재생하면 all-vacuous 게이트에서 닫힌다. 아래 단계는 전부 제대로 동작했고 여정 자체가
일어나지 않았을 뿐이다.

지금까지 드러나지 않은 이유는 이 픽스처들을 scripted 클라이언트로만 돌렸기 때문이다.
scripted는 프롬프트를 읽지 않고 정해둔 동작을 순서대로 내놓아 항상 완주한다.

목록은 `ELEMENT_LIMIT`으로 60개에 잘리고 현재 페이지만 설명하므로 실행이 길어져도 커지지
않는다. 작은 폼에서 턴당 약 21토큰, 상한까지 채워도 약 510토큰이다. 한 호출이 이미 캐시된
시스템 프롬프트로 5천 토큰 넘게 오간다. 반대로 실패한 탐색 하나가 유료 호출 5에서 11회를
태우고 재생 불가능한 시나리오를 남겼다. 같은 #15 작업의 나머지 절반인 시스템 프롬프트
캐시는 그대로 둔다. 그쪽이 실제로 턴 사이에 안 변하는 부분이다.

검증 결과: `packages/harness/test/core/stateless-prompt.test.ts`를 추가했다. 프롬프트만
읽고 답하는 클라이언트로, 목록이 있으면 동작하고 없으면 포기한다. 실제 모델이 한 그대로다.
수정 전 코드에 이 테스트를 걸면 두 개가 실패한다. explore의 고정 레이아웃 테스트는 생략
문자열 대신 페이지를 기대하도록 바꿨다. 전체 1,060개 테스트, 타입 검사, 빌드, 의존 경계
검사를 통과했다. 실제 Chrome과 소넷으로 폼은 5호출에 `savedValue: "alice"`, 상태 흐름은
8호출에 `orderCount: 1`로 완료를 확인했다.
