Legacy candidate construction captures `snapshot({perception:true})`, runs the perception adapter,
redacts configured input values, then constructs `PerceptionObservation`. Shared ranking filters
occlusion and limits the legacy prompt to 60 rows. The validated addressing table exists only
when the driver supports `locateRef`; its tokens are engine-owned `o<generation>-<slot>` values,
not raw driver handles. `page.bind` canonicalizes selection before ambiguity and action policy;
`decisionToStep` consumes the binding and uses `locateRef` to produce a persistent target.
`assertDecisionCurrent` and the Chrome exact-node validation remain in the execution path.

Legacy success is layered: locator dispatch records a substitution immediately; pipeline checks
step `expect`; surgical heal may run on divergence; `runScenario({heal:true})` can then rediscover
on blocked execution or failed goal assertions. Re-discovery is judged against original goals,
not newly proposed ones. Guards alone do not trigger it. Legacy locator substitutions can be
reported before final goal verification; the ordinary non-rediscovery return is not itself gated
on those goals. The pilot tightens confirmation only in its opt-in path, preserving old defaults.
`applyHeals` keys by target object identity; persisted targets discard runtime refs. Saving remains
the caller's job. A `replayEnvironment` repair is never returned as canonical.

## Official hosted contract

The official endpoint is `POST https://api.typesafe.ai/v1/systemone`, authenticated with a bearer
TypeSafe key. A request has `model`, structured `state`, and typed `questions`; a response has
resolved `model`, `answers` and token `usage`. The adapter consumes typed HTTP JSON directly; it
never impersonates `LlmClient`, serializes a decision into text, or uses the legacy JSON extractor.
[API reference](https://docs.typesafe.ai/api).

As of review, `jev-1.13.0` is the versioned model behind `jev-latest` and `jev-preview`. Direct API
input costs $0.042 per million tokens, with free output. The limit is 64k tokens across the full
request AND 32k for state plus the longest question; this one-question pilot is constrained by the
latter. Text/structured text only, no screenshot input. The adapter pins `jev-1.13.0` and records
the returned model; a different resolved version fails closed unless the caller explicitly chose
an alias. These are published specifications, not measured cost or capability here.
[Models](https://docs.typesafe.ai/models).

Choice returns the highest-probability key, a distribution over every declared key summing to one,
and confidence. Maximum cardinality is 255; the pilot reserves one for `none`, leaving 254 actual
candidates. It does not split an oversized set into model calls or silently truncate it.
[Choice](https://docs.typesafe.ai/primitives/choice).

Confidence is a 0..1 statistic of the distribution's concentration, not the probability of the
selected option and not an independently verified probability of correctness. The documentation
does not specify its exact formula on the confidence page. The adapter records it without
recomputing, substituting maximum probability, or promoting proof. Noul returns a yes probability
and has no separate confidence. Calibration is a supplier claim until tested on Cairn cases.
[Confidence](https://docs.typesafe.ai/confidence).

The supplier advertises 70–500ms end-to-end latency and notes that its published evaluations were
generally run on US West Coast laptops. That is neither an SLA nor this pilot's Korean-region
latency. No latency/cost advantage over the current healer has been measured here.
[Launch article](https://typesafe.ai/blog/introducing-system-one-models-and-jev).

Cloudflare now officially documents `typesafe/jev`, typed state/questions, Choice/Noul/Score,
distributions, confidence, resolved model and usage, via Workers AI binding or its account API.
Its page lists a 32,000-token context and directs pricing to the dashboard. This verifies a
supported intermediary candidate, not parity in pricing, pinned version control, retention or
latency. It is not wired into this pilot.
[Cloudflare model page](https://developers.cloudflare.com/ai/models/typesafe/jev/).

## Implemented opt-in contract and safety policy

`core/target-choice.ts` defines only `TargetSelector.select(TargetChoiceRequest)`, one locator
Choice result and audit data. It is deliberately smaller than a general `decide(state,questions)`
framework. The host supplies it through the existing Driver decorator at `runScenario`.

`runScenario` composes the selection policy with `createTargetChoiceRepair`. The policy lives in
`adapters/drivers/target-choice.ts`, outside the browser entry's runtime dependency graph; the
existing browser `SelfHealingDriver` export remains available. Direct decorator users pass
`choice: createTargetChoiceRepair({ selector, minConfidence, context, onDecision, secrets })`
and confirm the original step post-condition through `confirmChoice`. This replaces the initial
draft's inline `choice` configuration; the `runScenario.targetChoice` API is unchanged.

```ts
import { JevTargetSelector, runScenario } from "cairn-engine";

const result = await runScenario(frozenScenario, {
  driver,
  targetChoice: {
    selector: new JevTargetSelector(), // TYPESAFE_API_KEY, read only when repair is needed
    minConfidence: null,             // collect on broken target, withhold action
  },
  trace,
});
```

`targetChoice` and legacy `heal:true` are mutually exclusive. Removing `targetChoice` is the
rollback; ordinary replay is unchanged, or the host can explicitly restore its previous
`heal:true` setting. No CLI flag, suite-wide default, or new dependency is introduced.

The pilot calls Jev only after a typed locator `resolution` error, never for healthy replay,
transport/handler failures or a failing semantic assertion. The broken step must have an original
intent and nonempty `expect`, an unambiguous target object, and the scenario must contain a goal
assertion. The selected observation must be nonempty, within the cap and exactly addressable.
No input value, new action, locator, raw driver ref or arbitrary extension field is requested.
Candidate data is restricted to key, name, role, current duplicate ordinal, checked/disabled,
active-popup and clickable facts. Configured secrets are slotted in sent names/intent/target;
input values are omitted. Names remain untrusted data even inside JSON.

Keys are stable only within one observation, never durable element identities across re-renders.
The audit hashes the exact candidate set and records observation ID and keys. Persisting `nth`
does not make positional identity stable; unique anchors and post-conditions are still necessary.

| Condition | Pilot behavior |
| --- | --- |
| Healthy target | Original action, zero Jev calls |
| Missing intent/expect/goal, missing refs, empty/oversized candidate set | Fail the broken step, zero Jev calls |
| `none` | Abstain/fail; no dispatch, no heal, no fallback |
| Threshold unset (`null`) | Record proposed choice but withhold action |
| Confidence below explicitly supplied threshold | Abstain/fail |
| Missing key, bad JSON/type/model/distribution/usage, API error, timeout | Fail closed; no retry or model fallback |
| Disabled, unknown/expired reference, policy rejection, element gone | Fail closed even with high confidence |
| Action dispatched but original step expect fails | No confirmed heal or re-freeze |
| Step passes but final original goal fails or execution blocks | No healedScenario |
| Original goals verified, only health guard fails | Preserve existing goal/guard distinction; path may be returned, verdict remains red |

No numeric production threshold is supplied. The 0.7 in mock/browser contract tests exercises
branching only and is not a calibrated recommendation. The adapter's five-second timeout and
24,000 UTF-8-byte input cap are local resource policy, not provider performance guarantees or a
claim that bytes equal tokens. At most five target repair attempts are reserved by the decorator.
The provider adapter disables redirects/retries and discards raw errors/bodies. A service key is
never part of state or trace; host code must still keep it out of its own logs.

Existing `bind`, ambiguity, action policy, locator enrichment, current-observation validation,
exact driver dispatch, step polling and final original assertions all remain. Pilot `onHeal`
fires only after the original step expect passes. `healedScenario` additionally requires verified
original goals and an unblocked, non-vacuous run. Scores never compensate for mechanical failure.
An initial wrong click that succeeds without a resolution error does not trigger this selector;
its step expect can still fail the run, but this pilot does not replace surgical/outcome healing.

Trace header 1.7 adds `target-choice`: provider and model IDs, question/policy version,
candidate-set fingerprint, observation ID, distribution/confidence, threshold and fail-only
policy, decision outcome, latency and available usage. Existing step/assertion/case-end events
record execution, original post-condition and final verdict. Missing observation/preflight
failures are existing failed-step events, with no invented model response. Usage counts actual
Jev requests in `llmCalls`; failed calls without usage do not invent tokens. The proof grader is
unchanged. See `spec/core/trace.md` for additive-reader compatibility.

## Reproducible validation and paired evaluation

Commands run from this worktree after `npm run build`:

```sh
npm run typecheck
npm run build
npm run check:boundaries
npm run check:language
npm run journal:check
npm run test:workspace
npm run test:bench
npm run test:browser -w cairn-engine
node bench/jev/compare.mjs --out /tmp/jev-contract.json
node bench/jev/browser-smoke.mjs /tmp/jev-default.json
node bench/jev/browser-smoke.mjs /tmp/jev-preserved.json --preserve-network
node bench/jev/browser-smoke.mjs /tmp/jev-cumulative.json --cumulative-network
node bench/jev/compare.mjs --capture /tmp/jev-cumulative.json --out /tmp/jev-captured.json
```

Output paths must not exist. Reports are JSON with individual records, not p50/p95 claims.
`compare.mjs` defaults to offline scripted decisions, eight paired synthetic cases (four development,
four validation) and shared observations/candidates/gold. `--capture` uses the exact candidates
captured from the real #230 fixture instead. The two native prompts differ: legacy sees the
existing rendered/name prompt, Jev sees typed attributes/intent; no claim of identical prompt
information or isolation of model quality from prompt format is made. Both receive the same
underlying candidate data and original target. No live reference table is parsed to build Jev input.

The offline tests cover role changes, near/identical names, none, empty/capped/missing evidence,
reorder/nth, stale observations and nodes, malicious names, successful wrong clicks, missing/failing
post-conditions, final goal failure, confidence/threshold unset, timeout, HTTP errors and invalid
responses, policy and no-fallback behavior. A prompt-injection fixture proves transport containment
and bounded dispatch in tests, not resistance of the hosted model.

The browser experiment uses the actual stateful v3 server from #230, real Chrome and MCP 1.8.0,
scripted HTTP choice, fresh isolated browser/server/session for each run, document/API delay 0ms.
The scenario is explicitly authored with the original order POST and destination checks; it is
not a claim that the historical model-generated freeze included those checks. In fact the #230
report notes that its frozen assertions omitted `/api/order`, using a separate fixture oracle.

Results and exact counts are recorded in `jev-self-heal-results.md`. The key finding is already
clear: the default driver loses previous-page request evidence; preserved requests alone still
form a sliding window, which breaks the positional request watermark. A bench-only diagnostic
shim accumulates real wire rows by reqid and then the same assertions pass. It uses a private
transport hook strictly to diagnose the Driver contract, and is not a production integration.
The production driver has intentionally not been changed in this small pilot. A cumulative,
correctly scoped network evidence fix or a conforming consumer Driver is an adoption prerequisite.

## Paid evaluation gate, metrics, and adoption

No `TYPESAFE_API_KEY` or `JEV_API_KEY` was present in the process environment; no Jev secret/budget
configuration was found in this checkout. Existing Claude/Codex benchmark budget examples are
not a TypeSafe spending authorization. No provider request was made. Real Jev accuracy,
calibration, cost, latency, abstention and false-pass improvement remain unmeasured.

To run the prepared paired selection tool, supply an approved account with access to the pinned
model, a hosted baseline (the existing Claude/Codex CLI clients call hosted models), and a local
untracked configuration. Keep credentials in environment/secret manager. The config needs:

- `approval`: reference to the actual spending approval, not an invented approval string;
- `baseline`: source-compatible `backend`, explicit `model`, `maxCalls`, and `maxCostUsd` for
  Claude; Codex can use its existing explicitly approved `budgetMode: "calls"` and reports money
  unknown rather than guessing (do not combine calls-only mode with maxCostUsd);
- `jev`: `model`, `timeoutMs`, `minConfidence` (initially null), `maxCalls`, `maxCostUsd`, and a
  freshly confirmed `inputUsdPerMillion` rate (0.042 on the review date).

Start with eight paired calls per provider (one per labeled case), plus one paired captured
fixture selection, under separately approved caps. This is exploratory, not enough for adoption.
Cost ledgers stop at the call/cost threshold or unknown usage; an in-flight request can cross a
cost threshold, so it is a stop-after-accounting limit, not a provider-side spending lock.

```sh
node bench/jev/compare.mjs --live --config /secure/approved-jev.json --out /tmp/jev-live.json
node bench/jev/compare.mjs --live --config /secure/approved-jev.json \
  --capture /tmp/jev-cumulative.json --out /tmp/jev-live-captured.json
```

The runner alternates arm order and records first/reused-client condition and unknown provider
cache state. Each arm gets fresh snapshot-driver state. It reports selection accuracy (correct
choices/attempts), wrong dispatched selections/attempts, abstentions/attempts, fallback count,
individual latency, token usage and separately labeled provider/estimated cost. Actual repair
success and false pass are **null** in this selection-only runner; a synthetic dispatch is not a
browser outcome. Budget exhaustion marks a partial run incomplete. Keep errors separate from
semantic none and retain per-case records, not just a single aggregate.

The next browser evaluation must run identical frozen criteria in both arms, reset the app per
attempt, independently check fixture/product truth, and record: confirmed repairs/attempts,
wrong repaired targets, CI pass while product truth fails (false pass), abstention, fallback, total
model calls including failed/unknown-usage calls, billable cost and request/end-to-end latency.
Include the existing fault corpus and captured real-app cases, especially same-label duplicates,
reorders and adversarial names. Use paired repetitions and record process/browser/provider cache
conditions. Report individual results until a predeclared sample plan supports tail quantiles.

Tune instructions/thresholds on the development split only. Freeze rule, question, corpus and
model versions; then evaluate on separate withheld cases, including independent applications,
languages and hard negatives. These tiny hand-authored validation cases are exploratory, not a
statistical calibration set. Adopt only if wrong repairs/false passes improve at an acceptable
coverage/abstention rate, mandatory mechanical checks remain uncompromised, stale refs always
fail closed, subsequent replay returns to zero calls, and observed operational cost/latency fit
the approved budget. Unknown evidence and high model scores must never balance each other out.

## Follow-up: semantic assertions (design only)

Keep requirement authoring/review separate from runtime grading. Store immutable product-owned
criterion IDs/versions with requirement references, explicit definitions, positive/negative
examples, evidence requirements, indeterminate conditions, required/optional status, question
version and validated model/threshold policy. Freeze the reviewed manifest with the scenario;
runtime must not generate, rewrite or weaken it to fit an observed failure.

For a failed-login requirement: check authentication failure response and logged-out state in
code. Separately judge whether the visible message explains authentication failure, whether it
misleads the user into believing login succeeded, and only if the product requires it, whether it
explains retry. Ground each question in the actual message and required nearby evidence; the
current LlmCritic summary contains execution/network/console, not enough message text for this
proposed use, so an explicit text-evidence capture seam is needed first.

Implement a future registered `AssertionHandler`/Critic for reviewed semantic criteria, with Noul
probabilities interpreted by per-criterion validation, plus explicit indeterminate/error state.
Require every mandatory mechanical and semantic condition (AND); invert negative requirements
explicitly. Optional diagnostics cannot cancel a mandatory failure. Missing evidence, ambiguous
probability or provider failure must remain non-passing for CI. Do not shoehorn semantics into a
`custom` boolean that the current proof grader may call `work`; coordinate with #248 for an
inconclusive reason and truthful model provenance. Until that contract exists, fail closed with
an explicit judge failure, not passed=true. No automatic new rubric generation on a failed test.

Semantic assertions are explicit opt-in and introduce model calls on replay, just as existing
`expect` does. The default mechanical replay remains model-free. This follow-up is not implemented
in the locator pilot and must have its own evaluation and proof/trace review.
