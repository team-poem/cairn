## First-party runner track ended; engine hardening becomes the direction
*#158 · #168 · #104 · #8*

The first-party local web UI runner track was stopped: desktop-runner-style viewers are commoditizing
quickly, so the viewer is not where cairn wins, and the identity reconverges on the engine being the
product. The whole trace track was pulled by that prototype and `JsonlTraceSink` stays in the engine.
Three non-fixed tracks were set: repository restructuring with CLI and package abstraction isolation,
making scenario storage first-class, and discover and freeze reliability driven by measurement,
meaning the complexity-axis benchmark first and then fixing whatever the numbers point at.

## Consumer dogfooding produces a ranked list of promotion candidates
*references #114, #127, #132, #171, #182, #184*

A long-running embedding host contributed a list of things it had already built in its own layer
after real incidents, each filtered by whether another consumer would want it, whether it holds
without app knowledge, and whether a CLI makes it more urgent. Tier 1, made prerequisites by a CLI:
re-anchoring frozen absolute URLs to a run-time base; run-specific query strings frozen into
grounding, which makes every replay fail forever; a machine-readable failure class on the verdict so
CI can distinguish a broken app from a stale script from a bad environment; and first-class secret
slots, since frozen skills get committed and passwords would be baked in. Tier 2, driver quality: a
snapshot quiescence gate, since prompting the model to wait made things slower by adding waitFor
steps, so the mechanical fix was the right one; and occlusion-based hit testing to disambiguate
same-named elements when `nth` is absent. Tier 3, script hygiene: pruning scrolls that produced no
requests, which is deterministic from observation, and which is the only safe subset because stray
clicks and inputs can have DOM-only effects observation cannot separate. Explicitly not promotable:
widget-specific adapters, app-specific correlation checks, domain vocabulary maps and
framework-specific clickability detection, which belongs on the `perceive` seam.

## Assertion grounding freezes a stable endpoint prefix instead of the matched URL
*#172 · PR #178*

`deriveAssertions` froze the model's proposed match string verbatim, so when the same action POST
fires twice in a run the model distinguishes them by full URL and a one-shot id gets baked into the
skill, a structural false failure no replay can satisfy and one outcome-heal cannot fix. Grounding
now freezes the matched request's stable prefix, cut before the first dynamic segment with query and
hash removed, and drops instead of freezing when only the host survives, because a host-only
substring is satisfied by every request to that host and is worse than no check. Nine rounds of
cross-review shaped the dynamic-segment rule: it splits a segment on separators and cuts if any piece
has id shape, treats hex pieces as ids only when they contain digits, requires six digits minimum for
numeric pieces so `step-2` and `CVE-2024-21413` survive, and recognizes dates only in full form,
because a bare year and month is a fixed API version rather than a per-run value. The governing
priority is that under-cutting fails loudly while over-cutting passes silently, with the honest
correction that under-cutting is not cheap either, since an unmatchable assertion reruns outcome-heal
every execution. Further fixes: a 200 status floor so in-flight and error responses are never frozen
as success proof; matching through the same predicate the critic judges with, so freeze and judgment
ask one question; method preferred toward mutations, so the frozen check's strength no longer depends
on request arrival order; and benign-marked requests excluded from candidates, because marking an
endpoint benign means it is incidental and standing it up as proof inverts that meaning. Known
residue: substring matching cannot express a prefix and a suffix together, so a cut can lose the
action verb, recorded in the corpus as counterexamples.

## Same-name elements resolved by which candidate the page actually exposes to a click
*#176 · PR #181*

Same-role duplicates were already rejected, so the surviving first-match applies only across
differing roles, which is exactly the reported failure shape, a modal submit button against a
background nav link. That cross-role first-match is intentional, because the a11y tree routinely
wraps a link with an overlapping static text of the same name. The MCP text interface has no mapping
from uid to DOM, so the in-page probe returns roles rather than elements, intersected with the
snapshot candidates, and narrowing applies only when that leaves exactly one. Fixing the freeze path
matters most, because a wrong role frozen at discovery makes replay deterministically wrong forever.
Review found the probe was stricter than a real click, since the driver scrolls first and the
snapshot is not viewport-filtered, so a correct button below the fold was losing to a visible decoy;
the probe now answers reachable, occluded or unknown and refuses to narrow if any candidate is
unknown, narrowing only on measured occlusion.

## Discover CLI surfaces dropped action proofs as a warning
*PR #180*

When grounding drops a proposed request-status check, the fact only reached the trace, so a CLI user
silently received a skill with no proof the action happened, and the drop is not fail-closed, since a
single non-vacuous `navigated` still makes the scenario green even if replay only reaches the
destination without performing the action. `droppedProofReason` returns a reason only for grounding
gate events whose proposal was a request-status, so routine drops stay in the trace. Review inverted
the trigger: the message is about the freeze but the condition read the trace, so it fired when one
of two proposals had in fact been frozen and stayed silent when nothing was proposed at all; it now
asks `provesAnAction(scenario)`. Read-only flows warn even though they have no action to prove, which
is the noisy direction and is stated in the message.

## Stable query prefix retained for query-dispatched APIs
*PR #179*

Discarding query strings wholesale breaks APIs where the path does not name the action, because the
frozen value collapses and unrelated POSTs to the same endpoint satisfy the assertion. Keeping only
the keys does not help, since both proposals share the key and differ in value. `stableEndpointPrefix`
now appends a stable query prefix: parameters accumulate from the start of the query string until the
first run-specific value, judged by the same predicate used for path segments. It must be a prefix
rather than a filter, because the frozen value is matched as a substring, so retained parameters have
to be contiguous from the beginning; clients that reorder parameters across runs get no query frozen
at all, which is better than freezing an unmatchable value.

## Mixed-case id formats added to the cut rule
*PR #183*

Id detection knew only the hex alphabet and assumed any delimiter-free segment containing uppercase
was a camelCase route name, so ULIDs, nanoids, prefixed keys and JWTs passed straight through. Three
shape-based recognizers were added: exact 26-character Crockford base32 for ULID, three dot-separated
base64url parts for JWT, and a digit-density rule for alphanumeric tokens of eight or more
characters. Density is the axis that separates random tokens from camelCase route names, but density
alone also catches standard names such as `SHA256Digest`, so two or more separate digit runs are also
required at the 20 percent threshold, since standard names keep their digits in one clump while
generated tokens scatter them, with a single-run escape at 60 percent for human-readable ids such as
`ORD12345678`. All-lowercase tokens are excluded, because that is the most name-like shape. The
name-side counterexamples are the safety line for this rule.

## navigated and step URL expects freeze run-specific segments as wildcards
*PR #182*

The default `navigated` assertion and step URL expects went through `destinationKey`, which strips
only query and hash and bakes dynamic path segments in, the same permanent false failure as #172 and
more frequent, since `navigated` is attached by default without a model proposal. Prefix cutting
cannot be reused, because destinations match on path boundaries and a parent is not a child's arrival
point. `stableDestination` replaces each run-produced segment with a single `*`, preserving depth and
the surrounding segments. A destination consisting only of wildcards is rejected, and old skills have
no `*` so their behaviour is unchanged, guarded by a `Scenario.wildcards` marker. Review fixes:
generalization was bypassing the #96 idempotence precheck, so the guard now tests against the value
to be frozen; `navigated` degrades to a destination-less form stamped vacuous when the path has no
literal segment at all; and freeze and replay were using different locale-stripping options, which
only ever makes matching more lenient and therefore reintroduced the skip.

## Unprovable actions become a fail-closed rule, then an advisory pending measurement
*#184 · #169*

Refusing to freeze host-only values converted a loud failure into a silent pass: a scenario that
deleted something and then navigated drops the request assertion and keeps only a non-vacuous
`navigated`, so a replay that reaches the destination without deleting anything is green and heal
never runs. The existing fail-closed gates do not cover it, because they stand down as soon as any
non-vacuous assertion exists. Detection reads frozen data only and records the flag when both
conditions hold: no surviving non-vacuous request-status proof, and an observed successful non-benign
mutation with no stable path. Review then pushed it down to advisory, because the heal path bypassed
the gate, the watermark can count entry-load traffic, and third-party beacons with a numeric first
segment turned read-only tests permanently red. With no reliability benchmark there is no way to
measure the false-positive rate, so the agreed sequence is land advisory, measure, then flip. Arming
was restricted to same-site requests by suffix match, which is structural rather than a list of
analytics hosts.

## Verdict finalization consolidated into one function; truncated heal rediscovery now counts
*#186 · #189*

Verdicts were assembled in two places with the rule attached to only one, so a heal rediscovery that
hit the step cap and ended truncated was read by nobody: a partial state that happens to satisfy the
original assertions goes green, and that truncated path is refrozen for the next run to replay. A
truncated re-discovery is not a heal. `finalizeVerdict` is now the single funnel. `runScenario`
simply does not return a healed scenario for a truncated rediscovery, so the CLI, the suite and a
library caller all inherit the rule without remembering a flag; the same applies to a rediscovery
that completed but missed the goal. Goal means assertions minus the guards `no-failed-requests` and
`no-console-errors`, so a transient 500 during rediscovery does not discard a repair that reached the
goal, and the same predicate gates the trigger, since rediscovery cannot fix a 500 and would burn an
LLM call every run. `maxSteps` is now forwarded to heal rediscovery, otherwise a 40-step case
truncates at the default 20 after UI drift and stays permanently red.

## Probe fixtures run in CI, the one area that needs a real layout engine
*#185*

The in-page probe reads element boxes, hit tests and computed overflow, which only a layout engine
can answer; jsdom returns zeros, so unit tests could pin nothing but the script string, and three
bugs shipped green through three review rounds: a swallowed escape producing a whitespace rule that
deletes the letter s, scroll clipping decided on the wrong axis, and not knowing that fixed
positioning escapes an ancestor's overflow clip. All three were caught by a human opening a browser
by hand, meaning verification depended on someone's habit. Six fixture pages plus a browser test now
cover the layouts review actually produced, and each expectation asserts the whole bucket object,
because the probe's failure mode is putting a role in the wrong bucket rather than omitting it. The
browser suite is excluded from `npm test` so a browser-less clone still runs green, and CI runs it as
a separate job to keep verify's seconds-scale feedback.

## Unproven-action advisory surfaced through cairn suite
*#190*

The advisory was only visible in `cairn discover` and a discover-stage trace event, but suite attaches
no trace sink, so the path people actually run said nothing. The flag was added to the freeze payload
and to `SuiteVerdict`, read from the replayed scenario so it appears on cache-hit replays too, not
just right after discovery, since the flag lives in the frozen skill and cached replay is the path
people repeat. The trace header went 1.1 to 1.2, an added optional payload field being a minor.
