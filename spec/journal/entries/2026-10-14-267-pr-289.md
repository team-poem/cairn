# Enforce merge labels and explain blocked merges

_Drafted from [#289](https://github.com/team-poem/cairn/pull/289) by amazon7737. Edit this in place; do not delete and re-add it._

## What

Add the required `merge-label-policy` check for manual merges into develop. The check fails when `needs-merge` is missing, `no-merge` is present, or `status/1-needs-review` remains. A maintainer must explicitly replace the review label with the merge request; neither approval nor passing CI performs that transition.

The new read-only pull-request workflow reads current GitHub metadata instead of event labels, validates the triggering head, and checks again before success. Every open develop PR sharing that head must have eligible labels. The automatic merge bot uses the same label predicate and retains its approval, CI, clean-state, and expected-head safeguards.

cairn-pingu explains blocked merges in one concise English PR comment, for example `Merge pending: waiting for CI on the current commit.` Label, approval, CI, conflict, and other GitHub merge blockers are covered. A changed reason updates the bot's existing marked comment; an unchanged reason performs no write. The bot verifies its numeric identity, reads all comment pages, and leaves other authors' comments alone.

Queued notices recheck the PR's head, labels, draft status, review decision, and merge state before publishing. Existing notices resolve to `Merged.` or `Closed without merging.` after completion; no new completion comment is created. Comment failures warn without changing merge eligibility or hiding a label-cleanup failure.

## Why

The bot's existing label guard cannot prevent a maintainer from accidentally using GitHub's Squash and merge button. A required GitHub check applies the same label decision to that path.

A successful bot workflow previously left the reason for an unmerged PR only in the Actions summary. The PR comment makes the current blocker visible where a maintainer can act on it, without repeated comments from scheduled retries. This feedback begins when the updated trusted scripts land on develop.

`.github/rulesets/merge-label-policy.json` records the develop-only rule, pinned to the GitHub Actions App (15368). It preserves only the existing cairn-pingu App bypass (4138904), needed for journal and release-preparation pushes, and adds no human bypass. Existing approval and verify requirements, main, and release branches remain unchanged.

This is ordinary reviewed PR CI: no secrets, App token, or write permissions are available to the workflow. [Ruleset 25040192](https://github.com/team-poem/cairn/rules/25040192) is now active after confirming a completed check from GitHub Actions App 15368 on this PR's head. `gh pr checks 289 --required` lists the new check alongside verify, and the current human user has no bypass. No temporary human bypass or main release was needed.

The [policy check on commit 4abbd83](https://github.com/team-poem/cairn/actions/runs/38491069105/job/115616111077) correctly fails because `status/1-needs-review` remains. This is an expected policy rejection, not a test regression. Label event processing is asynchronous; wait for the refreshed check before merging. If a blocked PR sharing the head closes or moves away, rerun the remaining PR's policy job to refresh its conservative result.
