# Add run-local selected-item evidence bindings

_Drafted from [#332](https://github.com/team-poem/cairn/pull/332) by solp721. Edit this in place; do not delete and re-add it._

## What

Add opt-in `SelectedItemBinding` declarations and a `selectedItemEquals` custom check to verify that a detail view belongs to the collection member selected in the current run.

The Scenario stores the binding in its custom assertion's `params`; the host enables fresh evidence collection for each replay:

```ts
await runScenario(scenario, {
  selectedItemEvidence: { bindings: [binding] },
  custom: { "opened-resource": selectedItemEquals },
  judgmentKey: "resource-key-equals-v1",
});
```

- Read explicit `data-*` keys from the selected item before dispatch and independently from the destination after its readiness condition.
- Bind evidence to the run and action occurrence. Export comparison results and provenance without raw keys.
- Fail on contradictory keys; return required inconclusive when evidence is unavailable. Never retry the click because capture failed.

Initial support covers collection `click` replay in same-document Chrome flows. Full navigation and new tabs remain inconclusive; active bindings reject healing, `targetChoice`, and custom step-handler chains.

## Why

Selecting the current first item does not prove that the application opened its detail. If B replaces A at the first position, the run-relative check should accept detail B and reject detail C, while existing fixed-A assertions keep their original meaning.

Closes #327

  - 10 cases using independently fetched API records, including B→B success and B→C failure.
  - Late shadow/ARIA changes remain inconclusive; popup cleanup leaves no receipt in the original tab.
  - Each case makes one detail API request and zero model calls.
