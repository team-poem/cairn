## Capture evidence at selected execution checkpoints
*#314 · PR #328*

_Drafted from [#328](https://github.com/team-poem/cairn/pull/328) by solp721. Edit this in place; do not delete and re-add it._

### What

Add opt-in `evidenceCapture` for replay, discovery and recovery. Selected captures finish before the next action, with run-local provenance and validated action-prefix bindings.

```ts
evidenceCapture: {
  checkpoints: [
    { id: "editor", after: editorPath, elements: true },
  ],
}
```

- Keep `onStep` synchronous and reuse existing screenshots at shared boundaries.
- Separate capture policy from required verification. Missing required evidence stays inconclusive and prevents green.
- Reject unsupported bindings safely, preserve secret redaction, and include capture in run/workflow budgets.
- Bump judgment revision to 2 and trace version to 1.14.

### Why

Final confirmation does not prove that an intermediate screen was correct. Hosts need evidence from the intended execution boundary without racing later actions.

Capture deadlines reject late results but drain in-flight driver calls; they do not forcibly interrupt an unresponsive driver.

Closes #314

- 82 checkpoint regression tests, including recovery, cancellation, binding and redaction
- Four browser cases: correct state, wrong heading, disabled control and missing capture; all replayed with zero model calls
- Independent sub-agent review repeated after fixes
- Dependency boundaries, language and journal checks pass

## Report the executed healed step in replay progress
*#313 · PR #330*

_Drafted from [#330](https://github.com/team-poem/cairn/pull/330) by amazon7737. Edit this in place; do not delete and re-add it._

### What

`onStep` now reports `result.step`, the step that actually ran, matching the action entry and the `step` trace event.

`StepProgress` now extends `ExecutedAction`, and the pipeline builds the notification by spreading the action entry plus `index` and `screenshot`. The two can no longer disagree, which is how #313 happened: one hand-copied field came from the loop variable. `ExecutedAction.step` now documents that it is the step that ran.

One observable detail changes for hosts. Optional fields the action leaves out (`error`, `errorKind`, `skipped`) are now absent from the progress object instead of present with the value `undefined`. Reading them gives the same value; only an `in` check or a key enumeration would notice.

### Why

After a successful StepHealer replacement, `execution.actions[].step` and the trace described the repaired step, but `onStep` still received the planned step. A host that drives its progress timeline from `onStep` showed an action that never ran.

Closes #313

New `test/core/pipeline-step-progress.test.ts` checks, for every reported step, that `onStep`, the action entry and the trace event agree on step, `ok` and `skipped`, and that callback indices match action indices. It covers four cases:

- successful replacement reports the repaired step (fails on `develop`, passes here)
- ordinary execution reports each planned step
- a replacement that misses the expect reports the original step as failed
- a pre-satisfied expect reports the original step as skipped

The helper now compares each whole progress object to its action entry. Verdict and healing behavior are unchanged. The `targetChoice` wrapper in `run.ts` keys `confirmChoice` by the reported target. It never sees a replacement, because a StepHealer exists only with `heal`, which `targetChoice` rejects. A comment there now says so. `onStep` stays a synchronous notification.

## Expose the outcome-rediscovery eligibility decision
*#326 · PR #331*

_Drafted from [#331](https://github.com/team-poem/cairn/pull/331) by amazon7737. Edit this in place; do not delete and re-add it._

### What

Adds `rediscoveryEligibility(scenario, result)` to `cairn-engine` and `cairn-engine/browser`. It returns `{ eligible: true }` or `{ eligible: false, reason }`, where `reason` is `passed`, `budget`, `collection-position`, `environment`, `inconclusive` or `no-goal-failure`, the first that applies in that order. `runScenario` now calls it for its outcome-heal gate, so there is one policy implementation.

### Why

A host that composes `runHarness`, its own verification and `discover` had to copy the outcome-heal predicate from `run.ts`. A copy taken before #306 would still re-discover a collection-position scenario that `runScenario` refuses. Exporting the decision the engine itself uses keeps hosts in step as restrictions are added.

The decision accepts either the critic's raw verdict or a finalized one. A raw verdict has no failure class yet, so it is finalized against the result's actions first; a finalized one (green with `proof`, red with `failure`) is used as is.

The decision is pure. It does no driver or model work, it is not permission to dispatch (opt-in, cancellation and workflow admission still apply), and it is not acceptance (a re-discovery is still judged by `finalizeVerdict`). A host can add its own conditions on top but cannot loosen the engine's, because it only gets `eligible: true` when every engine rule passes.

`runScenario` behavior is unchanged. The operator's skip message is now a lookup by reason, so it cannot drift from the decision. An environment failure has no message of its own and keeps the wording it had before.

Closes #326

New `test/rediscovery-eligibility.test.ts` runs against both entry points:

- blocked runs and failed goals stay eligible for ordinary scenarios
- passed results are ineligible
- collection-position scenarios are ineligible even when blocked or a goal failed
- environment and budget failures are ineligible
- guard-only and inconclusive-only failures without a blocked step are ineligible, with distinct reasons
- a collection-position scenario with an environment failure reports `collection-position`
- a raw verdict with a budget stop or a transport-blocked step is ineligible, and a raw green with a blocked step is not read as passed
- a finalized verdict keeps its own failure class
- through `runScenario`, the inconclusive-only and guard-only skip messages are pinned exactly, with no model call

The existing `runScenario` outcome-heal tests pass unchanged. A throwaway script also compared the dispatch, skip and message decisions against the `develop` logic over 640 combinations of pass, failure kind, results, blocked, collection and heal, and they all matched. It is not committed because it embeds a copy of the old code.

Out of scope: dispatch admission (cancellation, workflow budget) and acceptance of a re-discovery are unchanged and already covered by their own tests. This decision only reads.

## Add run-local selected-item evidence bindings
*#327 · PR #332*

_Drafted from [#332](https://github.com/team-poem/cairn/pull/332) by solp721. Edit this in place; do not delete and re-add it._

### What

Add opt-in `SelectedItemBinding` declarations and a `selectedItemEquals` custom check to verify that a detail view belongs to the collection member selected in the current run.

The Scenario stores the binding in its custom assertion's `params`; the host enables fresh evidence collection for each replay:

```ts
await runScenario(scenario, {
  selectedItemEvidence: { bindings: [binding] },
  custom: { "opened-resource": selectedItemEquals },
  judgmentKey: "resource-key-equals-v1",
});
```

- Read explicit `data-*` keys from the selected item before dispatch and independently from the destination after its readiness condition.
- Bind evidence to the run and action occurrence. Export comparison results and provenance without raw keys.
- Fail on contradictory keys; return required inconclusive when evidence is unavailable. Never retry the click because capture failed.

Initial support covers collection `click` replay in same-document Chrome flows. Full navigation and new tabs remain inconclusive; active bindings reject healing, `targetChoice`, and custom step-handler chains.

### Why

Selecting the current first item does not prove that the application opened its detail. If B replaces A at the first position, the run-relative check should accept detail B and reject detail C, while existing fixed-A assertions keep their original meaning.

Closes #327

  - 10 cases using independently fetched API records, including B→B success and B→C failure.
  - Late shadow/ARIA changes remain inconclusive; popup cleanup leaves no receipt in the original tab.
  - Each case makes one detail API request and zero model calls.

## Add predicate-constrained collection selection
*#329 · PR #333*

_Drafted from [#333](https://github.com/team-poem/cairn/pull/333) by solp721. Edit this in place; do not delete and re-add it._

### What

Add explicit `Target.collection.choice` to select one eligible resource in DOM order. Reuse selected-item bindings so dependent actions and independent review evidence refer to the resource selected in this run.

```ts
choice: {
  version: 1,
  cardinality: 1,
  policy: "first-dom",
  identity: {
    kind: "attribute",
    scope: "item",
    attribute: "data-resource-id",
  },
  where: [{
    kind: "attribute-equals",
    scope: "item",
    attribute: "data-available",
    value: "true",
  }],
  maxReselections: 1,
}
```

The initial API supports hand-authored, same-document collection clicks. This also fixes StaticText receipts and preserves capture timeout diagnostics.

### Why

“Choose any available item” needs an explicit contract. A missing fixed target must not authorize selecting another resource.

When explicitly enabled, reselection is allowed once and only after the driver confirms the previous click was not dispatched. Uncertain mutations are never retried, original assertions remain unchanged, and fixed-target and positional behavior are preserved.

Closes #329

Additional verification:

- 257 browser tests passed.
- 17 predicate-selection and 10 existing selected-item MCP cases produced their expected outcomes, with zero model calls.
- Regression coverage includes StaticText continuity, wrong downstream resources, capture timeouts, and cancellation/budget expiry during reselection.
- Dependency boundaries, language and journal checks passed.
