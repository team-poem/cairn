# Expose the outcome-rediscovery eligibility decision

_Drafted from [#331](https://github.com/team-poem/cairn/pull/331) by amazon7737. Edit this in place; do not delete and re-add it._

## What

Adds `rediscoveryEligibility(scenario, result)` to `cairn-engine` and `cairn-engine/browser`. It returns `{ eligible: true }` or `{ eligible: false, reason }`, where `reason` is `passed`, `budget`, `collection-position`, `environment`, `inconclusive` or `no-goal-failure`, the first that applies in that order. `runScenario` now calls it for its outcome-heal gate, so there is one policy implementation.

## Why

A host that composes `runHarness`, its own verification and `discover` had to copy the outcome-heal predicate from `run.ts`. A copy taken before #306 would still re-discover a collection-position scenario that `runScenario` refuses. Exporting the decision the engine itself uses keeps hosts in step as restrictions are added.

The decision accepts either the critic's raw verdict or a finalized one. A raw verdict has no failure class yet, so it is finalized against the result's actions first; a finalized one (green with `proof`, red with `failure`) is used as is.

The decision is pure. It does no driver or model work, it is not permission to dispatch (opt-in, cancellation and workflow admission still apply), and it is not acceptance (a re-discovery is still judged by `finalizeVerdict`). A host can add its own conditions on top but cannot loosen the engine's, because it only gets `eligible: true` when every engine rule passes.

`runScenario` behavior is unchanged. The operator's skip message is now a lookup by reason, so it cannot drift from the decision. An environment failure has no message of its own and keeps the wording it had before.

Closes #326

New `test/rediscovery-eligibility.test.ts` runs against both entry points:

- blocked runs and failed goals stay eligible for ordinary scenarios
- passed results are ineligible
- collection-position scenarios are ineligible even when blocked or a goal failed
- environment and budget failures are ineligible
- guard-only and inconclusive-only failures without a blocked step are ineligible, with distinct reasons
- a collection-position scenario with an environment failure reports `collection-position`
- a raw verdict with a budget stop or a transport-blocked step is ineligible, and a raw green with a blocked step is not read as passed
- a finalized verdict keeps its own failure class
- through `runScenario`, the inconclusive-only and guard-only skip messages are pinned exactly, with no model call

The existing `runScenario` outcome-heal tests pass unchanged. A throwaway script also compared the dispatch, skip and message decisions against the `develop` logic over 640 combinations of pass, failure kind, results, blocked, collection and heal, and they all matched. It is not committed because it embeds a copy of the old code.

Out of scope: dispatch admission (cancellation, workflow budget) and acceptance of a re-discovery are unchanged and already covered by their own tests. This decision only reads.
