# 2.3.0

Archived 2026-09-12. 2 entries from the 2.3.0 cycle.

## Split the discover module and unify decision dispatch through the shared step handler

The large `switch` in `applyDecision` duplicated knowledge already held by `BuiltinStepHandler`, so
adding an action meant syncing five places with no `never` guard. It was replaced by `decisionToStep`
(a pure Decision to Step mapping with a `never` guard) plus execution through the same
`BuiltinStepHandler` that replay uses, so discover, replay and step-heal now share one execution
path. The 600-line `core/discover.ts` was split into `core/discover/{index, prompt, decision,
capture, grounding}`, with `index` re-exporting the public surface so external code only changes
import paths. Tests moved from colocation to a `test/` tree mirroring `src/`, with shared doubles in
`test/support/doubles.ts`. Behaviour is unchanged.

## Assign step expects retroactively from completed evidence instead of a single in-flight snapshot
*#81*

Issue #72 closed the replay race, but capture still took a one-shot snapshot: if the submit request
was still in flight (status 0), the step got no expect and fell outside detect and heal, reproduced
against a real app. A first attempt using bounded per-step polling was discarded because it added
another timing heuristic, assumed a driver contract where in-flight means status 0, and introduced a
two-second cliff. The adopted design has the loop record only a watermark per step (url and request
count) and decide expects retroactively at freeze time via `assignStepExpects`; the request log is
append-only with in-place status updates, so index slices stay valid and responses resolve naturally
while later steps run, removing the wait entirely. The only remaining bounded wait is the single
final observation for the last step's pending mutation, matching the `deriveAssertions` philosophy of
grounding on completed evidence.
