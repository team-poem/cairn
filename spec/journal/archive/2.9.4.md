## Wait for network and DOM quiet with explicit background request exclusions
*#175 · PR #281 · in-progress*

Chrome settling now measures current MCP request identities, response transitions and literal
pending rows alongside document mutations. A separate expiring observer retains only a revision
and leaves exact-reference guards intact. The same deadline bounds tool calls and sleep. Evicted
pending evidence stays unknown without holding the current wait open indefinitely.

Application-specific polling arrives through `ChromeDriverOptions.settle.ignoreRequests`, with
per-call overrides. These URL substrings affect idle accounting only: excluded requests remain
cumulative evidence and can still fail assertions. They do not become benign failures. Snapshot
lookup caches are cleared after waiting so deferred rendering is visible to later lookup.

The committed public-driver fixture reproduces the original pending-fetch and DOM races and
checks polling exclusions, an unrecovered 503, the mutation cap and a server-verified zero-call
replay. On one local comparison against develop 31cfed0, with a 400ms quiet interval, baseline
settle returned in 423ms while the fetch was pending; the fix waited 2764ms through the response
and deferred rendering. Excluded polling took 543ms versus 2212ms. These are fixture observations,
not population latency estimates. Reproduce with `npm run build && npm run test:settle` and the
runner's optional `--baseline-engine` argument. CI preserves the fixture's JSON result.

Typecheck, build, full tests, boundaries, language and diff checks passed, as did all 30 Chromium
probe/reference tests and the real MCP 1.8.0 document-reference and cumulative-network regressions.
No hosted model was used. Settling remains a bounded heuristic; missing DOM measurements fall
back to network waiting, and response headers do not prove body completion. CSS-only, frame or
shadow rendering and work scheduled beyond the quiet window still require `expect` or `waitFor`.

*#267 · PR #288*

_Drafted from [#288](https://github.com/team-poem/cairn/pull/288) by amazon7737. Edit this in place; do not delete and re-add it._

### What

Require a maintainer to remove `status/1-needs-review` and add `needs-merge` before cairn-pingu can merge an approved PR. A review label blocks merging even when `needs-merge` is also present, both at the initial check and immediately before the merge.

Add the required `merge-label-policy` check for manual merges into develop. The check fails when `needs-merge` is missing, `no-merge` is present, or `status/1-needs-review` remains. A maintainer must explicitly replace the review label with the merge request; neither approval nor passing CI performs that transition.

The new read-only pull-request workflow reads current GitHub metadata instead of event labels, validates the triggering head, and checks again before success. Every open develop PR sharing that head must have eligible labels. The automatic merge bot uses the same label predicate and retains its approval, CI, clean-state, and expected-head safeguards.

cairn-pingu explains blocked merges in one concise English PR comment, for example `Merge pending: waiting for CI on the current commit.` Label, approval, CI, conflict, and other GitHub merge blockers are covered. A changed reason updates the bot's existing marked comment; an unchanged reason performs no write. The bot verifies its numeric identity, reads all comment pages, and leaves other authors' comments alone.

Existing notices resolve to `Merged.` or `Closed without merging.` after completion; no new completion comment is created. Comment failures warn without changing merge eligibility or hiding a label-cleanup failure.

### Why

The bot's existing label guard cannot prevent a maintainer from accidentally using GitHub's Squash and merge button. A required GitHub check applies the same label decision to that path.

A successful bot workflow previously left the reason for an unmerged PR only in the Actions summary. The PR comment makes the current blocker visible where a maintainer can act on it, without repeated comments from scheduled retries. This feedback begins when the updated trusted scripts land on develop.

`.github/rulesets/merge-label-policy.json` records the develop-only rule, pinned to the GitHub Actions App (15368). It preserves only the existing cairn-pingu App bypass (4138904), needed for journal and release-preparation pushes, and adds no human bypass. This is ordinary reviewed PR CI: no secrets, App token, or write permissions are available to the workflow. [Ruleset 25040192](https://github.com/team-poem/cairn/rules/25040192) is now active after confirming a completed check from GitHub Actions App 15368 on this PR's head. `gh pr checks 289 --required` lists the new check alongside verify, and the current human user has no bypass. The [policy check on commit 4abbd83](https://github.com/team-poem/cairn/actions/runs/38491069105/job/115616111077) correctly fails because `status/1-needs-review` remains. ## Share execution budgets across discovery and repair
*#284 · PR #299*

_Drafted from [#299](https://github.com/team-poem/cairn/pull/299) by solp721. Edit this in place; do not delete and re-add it._

### What

Add optional model-call and elapsed-time budgets shared across discovery, replay judgment and repair. Each suite case gets its own allowance; entering another repair layer does not reset it.

```ts
await runSuite(cases, {
  budget: {
    maxModelCalls: 12,
    timeoutMs: 60_000,
  },
});
```

- Reserve model calls before dispatch, including concurrent requests. Failed or cancelled calls are not refunded.
- Propagate cancellation, wait for admitted work to settle, and reject late results without continuing actions or freezing an interrupted repair.
- Report exhaustion as `failure: "budget"`, with usage, available evidence and uncertain-operation metadata. Add a trace event and CLI exit code `5`.
- Expose CLI controls through `--max-model-calls` and `--run-timeout`. Keep budgets out of frozen scenarios and judgment identities.

The deadline is cooperative, not a hard process kill: non-cancellable operations must settle before the run returns. Model calls hidden inside custom components are not automatically counted.

### Why

Existing step caps, repair limits and transport timeouts bound individual operations, but not the combined work across discovery and repair. A run could stay within each local limit while exceeding the host's intended allowance.

This adds a shared stopping boundary without weakening assertions, introducing fallback models or adding model calls to healthy mechanical replay.

Closes #284

Regression coverage includes concurrent-call draining, custom action deadlines, cancellation, frozen drivers, final freeze failures and signal composition without `AbortSignal.any`.

## Report a refused navigation destination as refused, not missing
*#290 · PR #297*

_Drafted from [#297](https://github.com/team-poem/cairn/pull/297) by amazon7737. Edit this in place; do not delete and re-add it._

### What

When discovery refuses an observed destination at freeze (its leaf generalizes to `*`), the dropped `navigated` proposal now says the destination was observed and refused, instead of "the run reached no recorded destination". The three states the issue asks to tell apart now produce different reasons:

| State | Drop reason |
| --- | --- |
| Observed, refused, matches the proposal | `the run reached the proposed destination, but it generalizes to example.test/catalog/products/*, which does not name a page, so no destination check was frozen` |
| Observed, refused, differs from the proposal | `the run reached shop.co/products/*, not shop.co/cart` |
| No URL observed | `the run recorded no destination URL, so <proposal> could not be checked` |

### Why

The degraded assertion carries no `to`, and the drop message fell back to `grounded.to ?? "no recorded destination"`, which conflated "refused at grounding" with "never observed". It also reported every proposal as a mismatch in the refused case, so a real mismatch looked the same as a matching one.

### Scope

- Wildcard-leaf rejection, vacuity stamping, `vacuousBecause: "no-destination"` and replay are unchanged. The verdict-side message in `critics/assertion.ts` was already accurate and is untouched.
- The refused-case reasons print only the generalized destination, so they add no run-minted id beyond what the proposal already carried.
- The reason stays a string; a structured distinction would change the `onDrop` signature and the trace `gate` event, which is left for a separate decision.
- `types.ts`: the `no-destination` doc comment said "every path segment was run-minted"; since #182 it also covers a run-minted last segment and an empty path.

Noticed but left alone: for a literal-leaf wildcard like `/orders/*/done`, the existing branch compares the frozen wildcard form against the proposal's literal id, so a matching proposal is still dropped as a mismatch. The issue asks to keep that case's behavior, so the new test pins only its freeze.

Closes #290
