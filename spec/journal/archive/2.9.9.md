## Check the URL before spending a model call on page guidance
*#344 · PR #357*

Navigation can finish while the host is preparing guidance. Until [#357](https://github.com/team-poem/cairn/pull/357),
`discover()` and `explore()` could ask the model to act on the old page, only to discard its answer.
Both loops now check the URL after accepting guidance and before calling the model. If the URL
differs, even because it became known or unknown, the loop discards the observation and retries
under the existing expiration limit. The retry prompt uses the new observation's URL or `(unknown)`.

On a stable guided turn this costs one extra `driver.observe()`, without a new element snapshot.
The pre-call check adds no read when the provider returns no usable guidance. Navigation can still
happen during the model call, so the post-response and pre-dispatch checks remain necessary.

## Let hosts declare which controls must stay unchanged for a guided click
*#356 · PR #358*

A rotating promotion could invalidate a Checkout click even when the order had not changed.
Checking only the button would miss a change to the selected rows. [#358](https://github.com/team-poem/cairn/pull/358)
lets the host declare the controls the click depends on in `pageGuidanceScope` and opt in for
one observation with `freshness: "declared-scope"`. A click without an exact reference can then
proceed if its target is still unique and actionable and the driver can verify that its prerequisites
are unchanged. Whole-observation comparison remains the default; exact-reference actions keep their
existing checks.

In the Chrome/MCP cart fixture, both `discover()` and `explore()` clicked Checkout once while the
promotion rotated. Adding a second Checkout button or changing a row's checked state resulted in
zero clicks. If Chrome may have clicked but the driver cannot confirm it, the loop stops without
retrying or attributing the new page to an earlier step.

## Continue discovery across host-declared tasks
*#337 · PR #367*

_Drafted from [#367](https://github.com/team-poem/cairn/pull/367) by solp721. Edit this in place; do not delete and re-add it._

### What

Add `discoverWithTasks()` so a host can declare which tasks remain when the model says `done`. The engine checks that the current page still authorizes the same task before sending input, then reports route completion separately from verification.

```ts
const { scenario, progress } = await discoverWithTasks(intent, {
  driver, llm, baseUrl, taskPlan,
});
```

The task plan and progress report belong to this discovery run. Replay uses the recorded `scenario` as before.

### Why

In a flow that checks documents A, B and C, the model can open A and declare the job done. Restarting discovery risks opening A twice. A task plan lets the run continue with B and C under the original budget. It also lets the host report “visited B, title check failed” without treating B as either unvisited or verified.

Closes #337

The Chrome regressions also checked that switching documents at the same URL or changing a required checkbox sent no stale click. A separate read-and-accept flow kept its required scroll and replayed in a fresh browser with zero model calls.

## Compose per-target verification obligations from existing evidence APIs
*#338 · PR #361*

_Drafted from [#361](https://github.com/team-poem/cairn/pull/361) by amazon7737. Edit this in place; do not delete and re-add it._

### What

Add a synthetic consumer test and a recipe that check every target in an approved set (A, B, C)
with one predicate choice, one selected-item binding and one heading checkpoint per target. No
engine code or public API changes: existing #314, #327 and #329 composition meets every case.

### Why

A final-state assertion cannot show that each required target was checked. A correct heading on
C can hide a missing or failed check on B, and three visits to A look like three actions. #338 asks
first whether the current APIs can carry per-target obligations and aggregate reporting, and to
add engine code only for a demonstrated gap. The synthetic integration found no gap, so this PR
ships the recipe and regression coverage instead of a new API.

| Case | Supported by composition |
| --- | --- |
| A, B, C each pass | Yes, aggregate passes |
| Only A checked | Yes, B and C unconfirmed; verdict fails as `environment` |
| B wrong heading, C passes | Yes, B stays failed; verdict fails as `flow` |
| A visited three times | Yes, B and C stay unconfirmed (fixed clicks) or the run is refused before dispatch (choices) |
| Unknown membership | Yes, coverage `unknown` through a required-inconclusive scope check |
| Final destination without intermediate evidence | Yes, all targets unconfirmed |
| Route complete, verification unsupported | Yes, route 4/4 but not verified |
| Fresh replay after reset | Yes, prior-run checkpoints and bindings are rejected |
| Changed path or definition | Yes, refused, `path-changed`, or contract `changed` |
| Zero model calls; capture failure | Yes, `llmCalls` 0 and no repeated mutation |
| Single-final-state compatibility | Yes, serialized form and contract unchanged |
| No raw resource keys | Yes |

Closes #338

Disabling the run-ID, path-fingerprint and required-inconclusive guards that the recipe relies on
makes the new tests fail; each was restored.

Open questions:

- The host still writes the scope check, the runtime options derived from params, and the per-target summary. Is a recipe enough to close #338, or should those become exported helpers later?
- On the choice path, a repeated visit or a reordered target is refused before dispatch rather than reported as pending. Is that fail-closed shape the intended report?
- The 32-target cap comes from the selected-item binding limit. Is a larger bounded set needed?

## Preserve declared run-relative selection through discovery
*#343 · PR #363*

_Drafted from [#363](https://github.com/team-poem/cairn/pull/363) by amazon7737. Edit this in place; do not delete and re-add it._

### What

Discovery accepts host-approved `selections`. The model consumes one by naming its ID on a single click, the engine resolves the member with the existing #306/#329 collection logic, and the freeze keeps the declaration instead of the member discovery clicked. An optional `verify` freezes a #327 binding so replay checks that the destination belongs to the member selected in that run.

### Why

A host that approves "open the current first item" gets a frozen "open item B" from discovery, so replay reopens B or asks for repair when the list changes, even though the rule did not change. The reporting host works around this with host-side rewriting and by removing `expect`. This change carries the approved rule through discovery and freeze, so replay selects today's first item with zero model calls and can still reject arriving at the wrong item.

- Evidence observed after the selection is not frozen as fixed proof. No derived step expects from that point, no `navigated` or semantic `expect`, and only `request-status` checks a pre-selection request satisfies. Each drop is a `grounding` gate.
- An unused declaration truncates the result (`selection-unbound`). A failed selection stops discovery (`selection-failed`) with no retry.
- Trace 1.17 adds `gate: declared-selection` and the two truncation reasons.
- Phase 2 (plain links without a collection root) extends `Target.collection` and `verify` without changing this contract. See `spec/core/discovery-selection.md`.

Refs #343

`check:language`, `check:boundaries` and `journal:check` pass. `test:collection-selection` and `test:predicate-selection` still pass.

Open questions:

- A model click on a list member by ref still runs as an ordinary click and is caught only later as `selection-unbound`. Is binding by a model-named selection ID acceptable?
- Is the freeze filter after a selection too conservative?
- A selection click goes through the replay step handler, not `executeDecision`, so the #358 declared-scope pre-dispatch check does not run for it. The collection coverage checks do. Is that the intended split?
- Only the library `discover()` accepts `selections`. Should suite and CLI wiring follow in a later PR?

## Skip a declared redundant terminal click on replay
*#354 · PR #372*

_Drafted from [#372](https://github.com/team-poem/cairn/pull/372) by solp721. Edit this in place; do not delete and re-add it._

### What

Add opt-in cleanup for one case: when the last two steps click the same control, replay can skip the second click. `discoverForReplayCleanup()` keeps the original scenario, and `prepareReplayCleanup()` returns a separate approval tied to the recorded path and the host's declaration.

For a button that opens a summary panel, the saved path and the approved replay look like this:

    Saved:   goto → Show summary → Show summary
    Replay:  goto → Show summary

### Why

An unchanged URL or page does not tell us whether a click was redundant. If the panel closes while the model is choosing its next action, the second click actually opens it again.

Cleanup checks the page immediately before each click and requires both clicks to reach the same node. At replay, the host must still declare that one click is sufficient. If the declaration or judgment contract has changed, or a checkpoint or selected-resource check needs the second click, Cairn runs the full path.

Closes #354

## Select a declared position among plain links
*#343 · PR #375*

_Drafted from [#375](https://github.com/team-poem/cairn/pull/375) by amazon7737. Edit this in place; do not delete and re-add it._

### Why

A host can approve "open the current second post" before discovery. Its grid is made of ordinary links, though, with no accessible list root, so #306 collections could not express it. Legacy `nth` counts only links with the same name. Discovery therefore froze the link it happened to click, and replay reopened that post or asked for repair when the grid changed. The host worked around this by rewriting targets and removing `expect`. #363 carried the approved rule through discovery for ARIA lists. This PR does the same for plain links and checks that each replay arrives where the selected link points.

### What

- `Target.collection.links` declares the collection: `scope` (exactly one element), `member` (a `:scope` selector, where every match is a member), an optional `action` (the link inside a member), and an optional `group: "destination"`. `expectedCount` is required. Position is DOM order.

  ```ts
  { collection: { links: { scope: ".grid", member: ":scope > a" }, order: "dom", index: 1, expectedCount: 3 } }
  ```

- A member's position never depends on how it looks. A badged first card counts. An off-screen member counts and can be selected. A hidden member refuses the collection instead of shifting the position.
- With `group: "destination"`, a card whose image link and title link share one href counts once, and its first link is clicked. Equal URLs in different members are never merged.
- A new binding key pair, `{ source: { kind: "href" }, destination: { kind: "location" } }`, works as discovery `verify` or as a hand-written binding (`LinkSelectedItemBinding`). It compares the selected link's href, read by the final continuity guard immediately before the click, with the top-level URL of the document that received the click, after that step. The guarded click asks for a snapshot in its own MCP reply, and Chrome reads the departure marker and the arrival URL through that snapshot's `RootWebArea` UID. Another tab cannot resolve that UID, even at the same URL, and neither can a document that replaced it, so a decoy tab cannot answer either read. No tab title is changed. Fragments are dropped, the query is compared exactly, and a redirect is compared on where the browser landed.
- Chrome refuses a new-tab link before dispatch. The link's target is its own `target`, or the first `<base target>` when that attribute is missing or empty, as Chrome resolves it. Only an empty target or exactly `_self` counts as the same tab. A download, a same-document link or a non-http link is refused too. Discovery with the link `verify` dispatches through the same check, so it refuses these links before clicking too. If a document marker survives the click, the relation stays unconfirmed. Selecting B and arriving at C fails.
- A changed membership, order, selected node or href before dispatch refuses the click. There is no fallback and no retry. Replay makes zero model calls.
- Links have their own optional Driver ports: `observeLinkCollection`, `clickLinkWithDestination` and `readLinkArrival`. The existing ports keep their 2.9.8 types (`CollectionTarget`, `SelectedItemKey`, `DestinationResourceKey`, `SelectedItemBinding`), so a Driver written against 2.9.8 keeps compiling and never receives a link declaration or key. Without the link ports, a link collection is refused before any action, a link `verify` is refused in discovery, and a replay relation stays unconfirmed. `Target.collection` holds either form as `CollectionDeclaration`. `validateCollectionTarget` returns the form its argument is typed as, so a role-form target still returns `CollectionTarget`, as in 2.9.8. The self-healing wrapper forwards the link ports.
- Spec: `spec/core/link-selection.md`, with pointers from the collection, discovery-selection and selected-item specs and the guide.

Closes #343

## Measure a pointer-events none row as a disallowed pointer action
*#352 · PR #374*

_Drafted from [#374](https://github.com/team-poem/cairn/pull/374) by amazon7737. Edit this in place; do not delete and re-add it._

### What

The Chrome driver now fills in the `actions` eligibility map that #362 added. A row whose computed `pointer-events` is `none` reports `click`, `doubleClick` and `hover` as `disallowed`. A new test pins that a disallowed choice never reaches locator work, and that a snapshot published while the locator resolves does not move eligibility onto or off the bound decision.

### Why

Issue #352 asks the engine to tell observed context apart from action candidates, and to reject an action a Driver or host has measured as disallowed before it is dispatched. The model should then be able to choose the observed link. Missing hints must stay unknown, because a heading or a roleless widget with a working handler is still usable.

#362 shipped the prompt wording and the rejection path. It left two items open: a real Chrome measurement source and a dedicated asynchronous-enrichment test. This PR closes both. Nothing outside the Chrome probe and its tests changes, and the engine contract is untouched.

Why `pointer-events: none`: the pointer falls through to whatever lies beneath, so the driver reports a successful click that never reaches the row's handler. A real Chrome run confirms it, a direct `driver.click` on such a button returns normally and the page's handler never fires.

- A descendant with another `pointer-events` value can receive the pointer and bubble to the row, and a subtree of more than 64 elements is too large to scan. Both leave the row unknown. Only a positive measurement is reported.
- `type` and `select` are not measured, so a click restriction never blocks them. Nothing is removed from the listing.
- An on-screen `pointer-events: none` control already fails the foreground hit test and leaves the listing as occluded. This measurement covers rows the hit test cannot reach, such as offscreen or clipped ones. The value is therefore narrow, and the commit is separate if you would rather drop it.
- `inert` is not measured. Chrome drops an inert subtree from the accessibility tree (checked in real Chrome), so it never becomes a row.
- The page-side script's reply is parsed strictly. Only `disallowed` for `click`, `doubleClick` and `hover` reaches a row.
- Frozen replay gets no new gate. `spec/core/perception.md` records the measurement.

Closes #352
