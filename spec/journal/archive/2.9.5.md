## Derive reference-rejection recovery from the next observation
*#301 · PR #307*

_Drafted from [#307](https://github.com/team-poem/cairn/pull/307) by amazon7737. Edit this in place; do not delete and re-add it._

### What

After a rejected `ref`, discovery and exploration now give recovery advice that matches the observation the next decision actually sees. Locator repair (`SelfHealingDriver`) now uses ref instructions and examples only when that observation has references.

### Why

A rejected ref put `; choose a ref from the current observation` into the failure memory, even when the next observation had no references and the system prompt said not to send `ref`. That line also stayed in prompt history after the capability changed. `HEAL_SYSTEM` described ref responses regardless of what the observation contained. #246 and #261 fixed the initial prompts; this PR covers the recovery feedback and locator repair that were left out.

- The failure line now records only the diagnostic, `reference binding rejected: <reason>`.
- `failureBlock()` in `discover/prompt.ts`, shared by both loops, adds one recovery line when a rejection is in memory. Each prompt computes that line from `page.references`, which holds only the validated table. Page text that looks like a ref has no effect.
- `healSystem(hasReferences)` replaces `HEAL_SYSTEM`. The rule matches `stepHealSystem` in surgical repair.
- Invented, expired and contradictory refs are still rejected. A bad ref is never stripped so that its named target can run.

Closes #301

- New tests in `perception-prompt-contract` and `locator-heal-prompt-contract` cover:
  - discovery and exploration without references, including duplicates and page text that looks like a ref, followed by a valid named decision after the rejection
  - an empty observation
  - capability changes in both directions (references, then none, then references again)
  - a forged ref sent together with a name, with references present
  - locator repair with no table, with an empty observation, and when references disappear between repairs

  On the old source, 5 of the 6 new tests fail. The case with references present passes on both, as expected. The existing surgical-repair tests still pass.
- Dogfooding: N/A. This changes prompt text only, and the scripted LLM tests cover it.

## Add privacy-conscious selection diagnostics
*#302 · PR #310*

_Drafted from [#310](https://github.com/team-poem/cairn/pull/310) by solp721. Edit this in place; do not delete and re-add it._

### What

Add `selection` trace events to discovery, exploration, locator repair and surgical step repair. Trace format moves to `1.11`.

- Summarize `raw → perceived → eligible → selected` with counts, fixed role buckets, exclusion counts and cap omissions.
- Correlate prepared inputs through `observationId` and `decisionId`, independently of frozen step indices.
- Record `stage: "prepared"` explicitly: preparation does not prove model admission, a network request or an executed action.

The new payload contains no page names, values, URLs, prompts or Driver refs. Selection behavior stays unchanged, with no additional snapshots or model calls.

### Why

Current traces do not explain how much of an observation survives host perception, engine filtering and the selection cap.

These bounded summaries make that pipeline inspectable without recording candidate content. They do not identify individual omitted controls or replace model usage records.

Closes #302

## Exclude host-owned instrumentation roots
*#308 · PR #312*

_Written by hand from [#312](https://github.com/team-poem/cairn/pull/312) by solp721. Edit this in place; do not delete and re-add it._

This change reached develop inside the squash merge of [#315](https://github.com/team-poem/cairn/pull/315) (`a535eba`), whose branch was stacked on #312's. The squash replaced #312's commits, so GitHub never marked #312 merged and the journal bot, which reads one pull request number from the merge commit, drafted only #315.

### What

Add opt-in exclusion of host-owned instrumentation to `ChromeDevToolsDriver`, using explicitly registered DOM elements.

```ts
const ownership = createHostOwnedRootScope();
const driver = new ChromeDevToolsDriver({ hostOwnedRoots: ownership });
```

The same ownership policy applies to snapshots, target lookup, DOM text checks, semantic progress, and freeze/replay. Registration uses exact element identity and is revoked on detach or document replacement.

Human interaction, screenshots, and network/console evidence remain unchanged. Owned overlays still block application actions.

### Why

Embedded QA panels can enter Cairn's observations, shift duplicate target indices, or accidentally satisfy text assertions. Hosts need an explicit way to exclude their instrumentation without hiding it from people or adding app-specific heuristics.

This is a cooperative boundary, not a security sandbox. Registration supports top-level light-DOM roots; active ownership rejects frame boundaries explicitly. Existing positional scenarios must be re-frozen when changing the exclusion policy.

Closes #308

Real MCP regressions cover nested/reflected accessible names, preserved application text, host-only assertion rejection, and verbose-only dropdown selection with empty and active ownership. Scripted discovery → freeze → replay passes with **zero replay model calls**.

```sh

npm run test:host-owned
```

The real MCP regression is also wired into CI. This verifies browser behavior, not live-model performance.

## Detect repeated scroll cycles
*#309 · PR #315*

_Drafted from [#315](https://github.com/team-poem/cairn/pull/315) by solp721. Edit this in place; do not delete and re-add it._

### What

Add an opt-in scroll no-progress policy for discovery and exploration, with per-run state, policy composition, and bounded recovery.

```ts
const policy = composePolicies(
  originFence,
  createScrollNoProgressPolicy({
    tolerance: 4,
    recoveryTurns: 3,
  }),
);

await discover(intent, { driver, llm, policy });
```

The policy compares executed scrolls with subsequent observations. Missing coverage causes abstention; new content, actionable targets, and untried directions can allow recovery. Incomplete runs retain `truncationReason: "no-progress"` through suite and outcome-heal results.

### Why

Step limits bound execution, and freeze-time pruning removes unnecessary recorded scrolls. Neither detects repeated observed scroll cycles while discovery is running.

Keep this safeguard optional, preserve trusted goal checks and application error evidence, and leave deterministic replay unchanged. The detector adds no model calls; re-decisions can still consume them.

Closes #309

Additional coverage:
- 154 browser tests passed.
- Regression tests cover policy composition, concurrent runs, failed dispatches, target visibility changes, final-step goal checks, and diagnostic propagation.
- Real MCP checks cover body/closed-shadow abstention, asynchronous lazy-loading recovery, and HTTP 500/console-error preservation.
- A recovered flow replayed successfully with zero LLM calls.

## Settle no-judgment conflicts, wait on BLOCKED again, and request the workflows permission
*#318 · PR #320*

_Drafted from [#320](https://github.com/team-poem/cairn/pull/320) by amazon7737. Edit this in place; do not delete and re-add it._

### What

Restore the `CLEAN` merge-state gate in the cairn-pingu merge bot, reverting the BLOCKED relaxation from #319. #319's stacked-PR guard stays.

It also settles conflicts that need no judgment (`scripts/merge-conflicts.mjs`). When a same-repository PR is `DIRTY`, the bot merges develop into its branch in a temporary worktree:

- **Nothing left to merge** (the result equals develop): it comments and closes the PR. This is the #312 case; a replay of #312 against develop at #315 returns `landed`.
- **Every conflict block is one where the PR's side is already on develop** (either side left the base unchanged, or the PR only added lines that develop has in the same order): it pushes the merge commit to the branch. That is a fast-forward of the reviewed head, never a force push. Then it removes `needs-merge` and asks a maintainer to review the commit and request the merge again, because the resolved branch is new code nobody has reviewed.
- **Anything else** (including a PR deletion that develop modified, delete/modify conflicts, and fork PRs): the existing "resolve the merge conflicts" notice.

The merge only reads the branch as data; no code from the PR is executed.

A last change, requesting the `workflows` permission for the App token, will be added to this PR as a separate commit. See below.

### Why

#316 stayed BLOCKED to the App because it changes `.github/workflows/ci.yml`, and the merge token is issued with only `contents` and `pull-requests`. Once #319 let the bot try anyway, GitHub refused the merge:
