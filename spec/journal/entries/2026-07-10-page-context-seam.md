# 2026-07-10 — 소비자 발견: `pageContext` seam 제안 (스텝별 도메인 지식 주입)

- **출처:** 한비자 앱 임베드 도그푸딩. 코드 변경 없음 — seam 제안 저널.
- **실측 문제:** discover가 낯선 페이지에서 방황하는 근본이 "지각 부족"이 아니라 **장소 지식 부족**으로 드러남.
  에이전트의 1인칭 곤경 4가지가 반복 관측됨: ① 지금 어디인가(스냅샷은 요소 목록이지 장소의 *의미*가 아님)
  ② 다음 어디로 가야 하나(여정 뼈대를 몰라 그럴듯한 링크 전부 시도 — 실측 22스텝 방황, 외부이동 함정 링크 클릭)
  ③ 방금 행동이 됐나(앱별 피드백 관습을 몰라 재클릭 — 실측 재담기 4회 루프) ④ 뭐가 안 보이나(a11y 미노출 위젯).
- **소비자 해법(검증 중):** 페이지 카드 — URL 패턴 → "정체·가능 액션·피드백 관습·함정" 텍스트 카드를
  **매 스텝 현재 URL로 결정적 조회**(카드 한 장 ~100토큰, 검색 LLM 불필요)해 프롬프트에 주입. 카드 내용은
  앱 지식이라 소비자 몫(불변식 #1), 위계 명시("배경지식일 뿐, 화면 관찰이 우선" — 낡은 지식이 관찰을 이기면 안 됨).
- **현재 우회와 한계:** `DiscoverOptions`에 스텝별 컨텍스트 주입 지점이 없어 소비자가 **LlmClient 래퍼**로
  프롬프트 끝에 append 중. 동작하지만 — 엔진 프롬프트 구조를 모른 채 밖에서 붙이는 것이라 ① 정위치(페이지 관찰
  섹션 옆) 배치 불가 ② 엔진이 프롬프트를 개편하면 조용히 어색해짐 ③ 토큰 예산 관리가 엔진 밖. 우회는 우회다.
- **seam 제안:**
  ```ts
  interface DiscoverOptions {
    /** 호스트가 공급하는 현재-페이지 컨텍스트. 매 스텝 현재 URL로 호출되어
     * 반환 텍스트를 프롬프트의 페이지 관찰 섹션에 배치. null → 미주입.
     * (perceive와 대칭: perceive = 지각 보정 공급, pageContext = 장소 지식 공급) */
    pageContext?: (url: string) => string | null;
  }
  ```
  - **리트머스("다른 소비자도 원하나") 통과:** 자기 앱의 길잡이를 탐색에 주고 싶은 건 모든 소비자의 요구.
    perception seam(#132)이 "어떻게 보이나"를 소비자가 보정하게 했다면, 이건 "여기가 어디냐"를 소비자가
    알려주게 하는 것 — 같은 축의 쌍둥이 포트.
  - 엔진은 통로만: 내용 검증·앱 특수화 없음. 미지정 시 동작 불변(기존 seam들과 동일한 opt-in 계약).
  - 배치 시 고려: 인젝션 관점에서 이 텍스트는 _호스트 신뢰_ 입력(페이지 콘텐츠 아님) — 페이지 유래 텍스트와
    구분되는 섹션에 두면 좋음. 동기 함수로 충분(소비자 실측: URL 패턴 매칭이라 조회 비용 0).
- **채택 시 소비자 후속:** 익스텐션의 LlmClient 래퍼(`withPageGuide`)를 `pageContext:` 옵션 한 줄로 교체 후 격하.
- **효과 검증:** 소비자 쪽 도그푸딩으로 방황 감소(스텝 수·함정 클릭·중복 담기) 측정 예정 — 결과가 이 seam의
  우선순위 근거가 됨. 급하지 않음: 래퍼 우회가 도는 동안 검증 먼저.

## 추기 (같은 날) — 우회로의 한계가 실측됨

- 소비자 래퍼가 컨텍스트를 프롬프트 **뒤에** append했더니 탐색 회귀 발생: discover 프롬프트가
  `"Respond with JSON only."`로 끝나는 구조라, append된 카드(금지 문장 포함)가 마지막 발화가 되어
  출력 지시를 묻고 행동을 지배(담기 주저). prepend로 회피했으나 — "밖에서 붙이면 배치 위치를
  모른다"는 한계가 가설이 아니라 실측이 됨. seam이 정위치(관찰 섹션)에 배치하면 원천 차단되는 부류.
