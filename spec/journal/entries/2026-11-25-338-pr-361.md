# Compose per-target verification obligations from existing evidence APIs

_Drafted from [#361](https://github.com/team-poem/cairn/pull/361) by amazon7737. Edit this in place; do not delete and re-add it._

## What

Add a synthetic consumer test and a recipe that check every target in an approved set (A, B, C)
with one predicate choice, one selected-item binding and one heading checkpoint per target. No
engine code or public API changes: existing #314, #327 and #329 composition meets every case.

## Why

A final-state assertion cannot show that each required target was checked. A correct heading on
C can hide a missing or failed check on B, and three visits to A look like three actions. #338 asks
first whether the current APIs can carry per-target obligations and aggregate reporting, and to
add engine code only for a demonstrated gap. The synthetic integration found no gap, so this PR
ships the recipe and regression coverage instead of a new API.

| Case | Supported by composition |
| --- | --- |
| A, B, C each pass | Yes, aggregate passes |
| Only A checked | Yes, B and C unconfirmed; verdict fails as `environment` |
| B wrong heading, C passes | Yes, B stays failed; verdict fails as `flow` |
| A visited three times | Yes, B and C stay unconfirmed (fixed clicks) or the run is refused before dispatch (choices) |
| Unknown membership | Yes, coverage `unknown` through a required-inconclusive scope check |
| Final destination without intermediate evidence | Yes, all targets unconfirmed |
| Route complete, verification unsupported | Yes, route 4/4 but not verified |
| Fresh replay after reset | Yes, prior-run checkpoints and bindings are rejected |
| Changed path or definition | Yes, refused, `path-changed`, or contract `changed` |
| Zero model calls; capture failure | Yes, `llmCalls` 0 and no repeated mutation |
| Single-final-state compatibility | Yes, serialized form and contract unchanged |
| No raw resource keys | Yes |

Closes #338

Disabling the run-ID, path-fingerprint and required-inconclusive guards that the recipe relies on
makes the new tests fail; each was restored.

Open questions:

- The host still writes the scope check, the runtime options derived from params, and the per-target summary. Is a recipe enough to close #338, or should those become exported helpers later?
- On the choice path, a repeated visit or a reordered target is refused before dispatch rather than reported as pending. Is that fail-closed shape the intended report?
- The 32-target cap comes from the selected-item binding limit. Is a larger bounded set needed?
